# OCR lab: talk notes and how to verify everything

Written 3 Nov 2026 after the observability work. Every number here was measured on the lab's
single L40S node, never on the mock.
Visuals: `talk/visuals/15-17-*.png`, regenerated by the scripts in `talk/visuals/source`.

## 1. The most important things for the talk

1. **Open weights let you see inside the model server, and make it yours to run.** A hosted API
   gives you latency and a 429. Here every request splits into queue, prefill and decode, next to
   KV cache, GPU power and the scheduler's decision. Cold start (431 s on restart, 683 s fresh) is
   also yours.
2. **One request is mostly silence.** 89% of a 12.8 s extraction is decode, and with thinking on the
   client sees nothing for about 10 s while the model reasons (476 of 651 output tokens).
3. **GPU utilization lies.** It reads ~100% with 1 request and with 24, while generated tokens/s
   went 52 → 961 (18.6×), latency rose only 27% and cost per 1,000 extractions fell $3.22 → $0.18.
   Waiting requests, KV cache, tokens/s and power tell the truth. (`visuals/16`)
4. **Quality is a signal, not a feeling.** Passport check digits give label-free correctness in
   production. Thinking on vs off is a quality/latency/cost trade that only a quality signal shows:
   on the latest batch, on = 0 wrong fields but 3 of 40 unanswered and 2.7× slower; off = 2 wrong
   fields, all answered. An earlier batch went 13 wrong (off) vs 0 (on). (`visuals/17`)
5. **Correlation needs every hop, and OTLP + W3C trace context is what joins them.** After the
   fixes one trace runs Envoy → API → llm-d → vLLM, and one request ID appears in every log and in
   vLLM's own request name.
6. **The trace found a real bug.** Each request ran the llm-d scheduler 16 times (168 spans, 160 of
   them scheduler). Envoy Gateway put one endpoint-picker filter per route path in its listener.
   A one-rule route fixed it: 23 spans, 1 scheduler run.
7. **Telemetry needs tests too.** It failed silently, always in the "looks healthy" direction: the
   first 502 left availability at 100%, healthy SLO panels went blank, one idle `NaN` could blank a
   28-day SLO, Alertmanager rejected its new config and kept the old one, the PII rule deleted
   `service.name`, a cold-start rule read 6,181 s instead of 411 s.
8. **Telemetry describes the request, never its content.** No image, prompt, reasoning or field
   values anywhere; visitor IPs are cut to their network.

## 2. OTLP was the spine of the lab

**What to say:** every signal reaches storage as OTLP, through one OpenTelemetry Collector. That
single choice is what made privacy, cardinality, sampling and correlation enforceable in one place,
and it's why the backends are replaceable.

How each piece gets into OTLP:

| Source | How it becomes OTLP |
|---|---|
| FastAPI API | OTel SDK pushes traces, metrics (with exemplars) and logs over OTLP/HTTP |
| vLLM | `--otlp-traces-endpoint` pushes spans (`llm_request` with `gen_ai.latency.*`) |
| llm-d scheduler | KServe's `tracing` block on the LLMInferenceService pushes spans |
| Envoy Gateway | `EnvoyProxy` resource pushes spans over OTLP/gRPC as service `envoy` |
| vLLM, llm-d, Envoy, DCGM, kube-state-metrics metrics | Prometheus format, scraped by the collector's `prometheus` receiver and converted |
| Pod CPU/memory | `kubeletstats` receiver |
| Pod logs, Kubernetes events | `filelog` and `k8sobjects` receivers |
| Alerts | Alertmanager webhook → `webhookevent` receiver → OTLP logs |

Out of the collector, all OTLP: Tempo (gRPC), Prometheus's native OTLP endpoint (keeps exemplars,
Prometheus scrapes nothing), Loki's native OTLP endpoint.

The points worth making on stage:

- **One pipeline, one policy.** Fail-closed span attributes, value scrubbing (MRZ lines, base64
  images, bearer tokens), IP masking, the cardinality guard and tail sampling apply to every signal,
  whatever produced it. A developer who adds `passport.surname` to a span loses it at the collector.
- **Resource attributes are the join keys.** `service.name`, `k8s.pod.name`, `k8s.namespace.name`
  are what let a metric, a span and a log line be about the same thing. Two real bugs were exactly
  this: the redaction rule deleted `service.name` (Tempo lost every service), and engine logs were
  named `qwen3-5-9b` while their spans said `vllm`, so trace → logs found nothing.
- **Context propagation is the other half.** OTLP carries the data; W3C `traceparent` carries the
  identity across hops. Envoy, nginx (pass-through), HTTPX, Envoy again, the scheduler and vLLM all
  honour it, which is how one trace spans four services.
- **Semantic conventions make it portable.** HTTP and GenAI conventions (`gen_ai.usage.input_tokens`,
  `gen_ai.client.operation.duration`, `gen_ai.response.finish_reasons`) mean a dashboard built for
  this app would read another GenAI app the same way.
- **Honest limits.** Most engines still expose Prometheus metrics, not OTLP; nginx has no OTel at
  all; vLLM logs carry no trace ID. OTLP is the transport inside the pipeline, and the collector
  translates. Translation has costs: OTLP → Prometheus adds suffixes (`_total`, `_seconds`), which
  broke panel queries, and a counter's first sample of 1 is invisible to `rate()`.
- **The collector becomes a single point of failure.** Its own metrics leave on a separate path
  and are alerted on (`TelemetryExportFailing`, `TelemetryRefusedByCollector`).
- **LLM requests stretch tracing assumptions.** Tail sampling decided 15 s after a trace started
  while requests run up to 30 s; the wait is now 70 s. The 8 s "slow" rule kept every thinking
  request; it's now 25 s.

## 3. The lab, piece by piece, and how to verify each one

### Running it

```bash
# start your GPU machine and open your admin tunnel (VPN or SSH), then:
export KUBECONFIG=~/.kube/ocr-lab.config                       # written by scripts/provision.sh
kubectl -n monitoring port-forward svc/kps-grafana 3000:80     # Grafana (set your own password)
export OCR_LAB_URL=http://<your-app-host>                      # used by talk/visuals/source/*.py
```

Extraction works about 8–9 minutes after the machine starts (model load and compilation). Keep the
app on plain HTTP only for synthetic or specimen images, and stop the machine when you're done.

### What runs where

| Namespace | What | Version |
|---|---|---|
| `default` | vLLM (`qwen3-5-9b-kserve`), llm-d scheduler (`…-router-scheduler`), API, frontend | vLLM 0.31.0, EPP 0.10.0 |
| `kserve` | KServe and LLMInferenceService controllers, the Gateway | KServe 0.21.0 |
| `envoy-gateway-system` | Envoy Gateway and its Envoy proxy | EG 1.8.1, Envoy 1.38.1 |
| `monitoring` | OTel Collector (DaemonSet), Prometheus, Alertmanager, Grafana, Loki, Tempo, DCGM exporter, kube-state-metrics | collector 0.162.0, Prometheus 3.15, Loki 3.6, Tempo 3.1, DCGM 4.8.4 |
| `lws-system`, `cert-manager`, `envoy-ai-gateway-system` | dependencies of KServe / llm-d | |
| `kube-system` | K3s 1.36, NVIDIA device plugin | |

Infrastructure: one preemptible L40S VM with a separate persistent disk for the weights, and a
WireGuard tunnel for admin access. Bring your own (any provider, or a workstation). Everything after
that is `scripts/bootstrap.sh` → `scripts/lab-up.sh` → `observability/install.sh`.

### Request path

Browser → Envoy Gateway (port 80) → nginx (`/api`) → FastAPI → Envoy (model route, API key) →
llm-d scheduler (ext_proc) → vLLM → GPU. The API checks the MRZ check digits and returns JSON.

### Verify, layer by layer

Run these in Grafana → **Explore**, or with `kubectl` where shown.

**Application**
- PromQL `sum by (outcome) (increase(ocr_extractions_total[10m]))` – every outcome series exists,
  even at 0 (counters start at 0).
- PromQL `histogram_quantile(0.5, sum by (le) (rate(ocr_extract_duration_seconds_bucket{outcome="ok"}[5m])))`
  – about 12–16 s with thinking on.
- Upload a passport and read the `x-request-id` response header; LogQL
  `{service_name=~"envoy|ocr-frontend|ocr-api|inference-scheduler"} |= "<that id>"` should find it
  in all four, and the trace's `chat qwen3-5-9b` span shows `gen_ai.response.id = chatcmpl-<that id>`.

**Edge (Envoy Gateway)**
- TraceQL `{resource.service.name="envoy"}` – traces now start at Envoy (`ingress` span).
- LogQL `{service_name="envoy"} | json | trace_id != ""` – access log lines carry `trace_id`, and
  `downstream_remote_address` ends in `.0` (masked).
- `kubectl -n kserve get envoyproxy,clienttrafficpolicy` – `ocr-lab-telemetry` and `ocr-lab-request-id`.

**Routing (llm-d)**
- One trace should have exactly one `pick_endpoints` span and ~23 spans in total.
- PromQL `sum(increase(llm_d_epp_scheduler_attempts_total[10m]))` equals the number of requests.
- `kubectl -n default get httproute qwen3-5-9b-kserve-route -o yaml` – one rule.
- Envoy's filter count:
  `kubectl -n envoy-gateway-system port-forward deploy/envoy-kserve-kserve-ingress-gateway-deaaa49b 19000:19000`
  then `curl -s 'localhost:19000/config_dump?resource=dynamic_listeners' | grep -o 'ext_proc/endpointpicker[^"]*' | sort | uniq -c`
  – it was 16 before the fix. (After the fix I saw 17 once while the proxy was restarting; recheck.)

**Inference (vLLM)**
- PromQL `sum(vllm:num_requests_running)`, `sum(vllm:num_requests_waiting)` (waiting stayed 0 up
  to 24 at once), `max(vllm:kv_cache_usage_perc)` (9% at 24).
- PromQL `sum by (finished_reason) (increase(vllm:request_success_total[1h]))` – `length` counts
  the runaway reasoning that returns no answer.
- LogQL `{service_name="vllm"} |= "Maximum concurrency"` – the engine's own capacity statement.
- Open the `llm_request` span: `gen_ai.latency.time_in_queue`, `…prefill`, `…decode`, `…time_to_first_token`.

**GPU (DCGM)**
- Dashboard **GPU · DCGM** → "Utilization vs real work". Compare with tokens/s on **Inference
  engine · vLLM**. Time ranges with data: 3 Nov 22:54–23:01 (ramp 2→24) and 23:32–23:38 (1 vs 24).
- PromQL `count(DCGM_FI_DEV_POWER_USAGE)` = 1 (no double collection).
- DCGM matches `nvidia-smi --query-gpu=utilization.gpu,power.draw,temperature.gpu,memory.used --format=csv`
  on the VM. Since 4 Nov it reads every 5 s; before that every 30 s, so runs before 4 Nov have
  coarse GPU data (the "83%" for one request rests on about 3 readings).

**Kubernetes**
- PromQL `ocr:model_pod_time_to_ready_seconds` – cold start, 400–700 s.
- LogQL `{service_name="k8s-events"}` – Scheduled, Pulled, Unhealthy (normal during start-up).

**Pipeline, privacy, alerts**
- `kubectl -n monitoring exec alertmanager-kps-alertmanager-0 -c alertmanager -- amtool alert add TestAlert severity=info --alertmanager.url=http://localhost:9093`
  then LogQL `{service_name="alertmanager"}` within a minute.
- PromQL `ocr:price:gpu_hourly_usd` = 0.87; `slo:objective:ratio` shows 25 s latency and 75% MRZ.
- PromQL `sum(rate(otelcol_receiver_refused_spans_total[5m]))` = 0.
- In any trace, no attribute holds a name, number or MRZ line; `redaction.redacted.count` shows
  what the collector removed.

## 4. Numbers you can quote (3 Nov 2026 unless noted)

| Claim | Value |
|---|---|
| One request, thinking on | 12.7 s p50; decode 89%; first content ~10 s |
| 1 at a time vs 24 at once | 52 → 961 tokens/s; 4.5 → 81 extractions/min; p50 12.7 → 16.2 s; 206 → 278 W; util 83% → 100%; $3.22 → $0.18 per 1,000 |
