Observing open weights

With open weights the model server is yours, so you can see inside it. The hard part stops being how to get signals and becomes knowing which ones to trust.

Every number comes from runs on the real GPU, and none from the mock. The first trace is one request, the first after a restart on 31 Oct 2026, captured before the fixes on 3 Nov 2026; read it as an example and not as a typical value. Accuracy figures come from 40 deliberately degraded synthetic passports and are directional. Metric, span and log names were read from the running stack.

What I would mention

  • You can finally answer "why is it slow?"A hosted API gives you a latency number. Here the same request splits into queue, prefill and decode, next to memory, power and scheduling.
  • One request is mostly silence89% of a 12.8 s extraction is decode. For about 8 s of it the engine is generating reasoning and the client has received nothing.
  • Classic saturation signals lieGPU utilization read 100% with 1 request and with 64, while throughput kept climbing. KV cache and waiting requests tell the truth.
  • Quality needs its own signalAvailability and latency stay green when the answer is wrong. Passport check digits give a free, label-free check, and even that one misleads.
  • Correlation is only as good as its weakest hopAt first only the API linked metric to trace to log. After edge tracing and one shared request ID, a single ID now runs from Envoy to vLLM's own request name.
  • Observability needs tests tooSeveral bugs made the system look healthier than it was, including a real 502 that left availability at 100%, and a gateway that quietly ran the scheduler 16 times per request.

4 · One request12.8 seconds, drawn to scale

This is trace a3e2297e…, one synthetic passport through the public app, captured before the fixes. It's the strongest single slide you have, because it joins all three signals on one timeline. The table below it shows the same request type after the fixes.

What to point at

  • Decode is 11.41 s of 12.83 s. Queue is 43 ms. This request wasn't waiting for anything except generation.
  • 649 tokens in 11.41 s is 57 tokens/s, which is exactly what people mistake for the GPU's limit.
  • Envoy took 0.92 s longer than the API, and at the time only the access log could see it. With edge spans, the new trace shows 0.81 s at the edge before the API starts.

What's odd

  • 160 of the 168 spans came from the scheduler: 16 runs of 10 spans. Only 8 spans did the actual work. Fixed: now 23 spans per request.
  • Engine says first token at 1.06 s, client says 9.54 s. Both are correct, because they measure different things.
  • Reasoning takes about 464 of the 649 output tokens (estimated). No metric separates the two.

9 · Uncommon thingsWhat people probably haven't seen

Label-free ground truth

ICAO check digits let you measure correctness in production with no labels and no second model. Most LLM apps have to build this. Ask the audience what their equivalent is: a schema, a checksum, a total that must add up.

Scheduler decisions as spans

Each scorer is a span with its weight and score, so "why this replica?" can be answered from a trace. With one replica the scores don't decide anything, so say that plainly.

Telemetry that can't leak by accident

Span attributes are fail-closed: a new passport.surname attribute is dropped at the collector, and tools/pii-probe proves it. The first version also deleted service.name, and Tempo lost every service. redaction.*.count on spans is the only sign that something was removed.

Tail sampling meets slow requests

The sampler decided 15 s after a trace's first span, but requests can run 30 s, and the collector counted 12 late spans after one restart. Lower the rate and late failures could be dropped. The wait is now 70 s, longer than the API's 60 s model timeout, and the "slow" rule moved from 8 s, which kept every thinking request, to 25 s.

Testing your observability

What worked: run every dashboard query and list the empty ones (79 of 83 had data, the other 4 were expected), then compare dashboards with k6, and stop and rebuild the lab. An empty-query check still missed NaN.

What telemetry costs

168 spans per request, 160 of them scheduler, until a route fix made it 23. 583 metric names at idle. inference_* and llm_d_epp_* look like two names for the same data (both read 16 attempts). The cardinality guard keeps request IDs off metrics; nothing yet limits span volume.

Privacy in the plumbing

The app logs no passport data, yet Envoy stored real visitor IPs, even though the API only sees a private address. The collector now cuts every public IPv4 to its network in logs and spans. Your access logs can be the personal data you forgot about.

History across shutdowns

A stopped lab kept its metrics: a marked count read 14 before and after the restart. A rebuild wipes them. For a preemptible GPU, decide on purpose which history has to outlive the node.

10 · What we aren't showingSay these out loud, because it adds credibility

Not instrumented

  • Browser experience. No RUM, so upload time and perceived wait are unknown.
  • nginx spans. nginx passes the trace through but adds no span of its own; Envoy's router span covers it.
  • Reasoning versus answer tokens. Only estimated from two timestamps.
  • Node level. No node-exporter, so disk throughput isn't a metric. The slow disk was found with a log line and dd.
  • Host logs. Bootstrap journal, kubelet and dmesg never reach Loki, yet they found many of the bugs.
  • Image quality. No signal for blur, rotation or resolution, the likely causes of bad reads.
  • Continuous profiling. No CPU or GPU profiles of the API or vLLM.

Can't be shown on this lab

  • Real GPU activity. SM, tensor and DRAM activity crash the exporter on this VM, and that would be the real answer to "is the GPU busy?"
  • Load balancing. One replica, so the balance panels have one line and the router has no choice to make.
  • Autoscaling. One GPU, no scaling events.
  • The throughput ceiling. Never reached at 64 requests.
  • Thermal drift. Tests lasted minutes, so sustained heat and throttling are untested.
  • Production quality. The accuracy data is 40 synthetic passports.

Built but not demonstrated yet

  • Paging a person. Alerts now land in Loki, but nothing sends them to Slack or e-mail.
  • SLO targets under real traffic. They were reset from lab measurements (25 s latency, 75% MRZ validity) and haven't met real users yet.
  • Model loss under load. The Cold start dashboard is built for it, but it hasn't been recorded.
  • Hosted comparison. The panel exists, with placeholder prices and no hosted traffic.
  • Security signals. 401s and scanners are in the logs with no panel, and the public app has no HTTPS or rate limit.

Left out on purpose

  • Prompts, images and model output. The price is real: you can't open a trace and read why one extraction went wrong. You can only rerun the image if you have it.
  • Reasoning text. It may repeat passport data, so it's treated like the output.
  • User feedback. The app has no corrections, which would be the best quality signal of all.
  • A golden set in CI. Accuracy was scored by hand, so a model change wouldn't be caught automatically.

11 · Live demoOne path that shows everything

Start the load first, since panels take a minute to fill. Keep a recording as a backup, because cold start alone is about 9 minutes.

k6 run -e BASE_URL=http://<public-ip>/api -e SCENARIO=minute -e PEAK_USERS=40 loadtest/k6/ocr-users.js
  1. SLOs and quality: show latency under load, click an exemplar dot, and land on one real trace.
  2. The trace: open llm_request for queue, prefill and decode, then compare the two first-token numbers.
  3. Its logs: jump from the API or Envoy span to its logs on trace_id, and show there's no passport data in them. From the vLLM span, the same button shows the engine's lines from that moment.
  4. One ID: take x-request-id from the response header and search Loki for it: Envoy twice, nginx, the API, the scheduler, and chatcmpl- in the trace.
  5. Inference: show waiting at zero and KV cache low. The system is healthy and not saturated.
  6. GPU: put utilization next to generated tokens, the moment "100%" stops meaning anything.
  7. Routing: open a scorer span, then tell the story of the 16 runs per request and the one-line route fix.
  8. Cold start, recorded: delete the model pod during load and show errors, events and vLLM start-up lines on one screen.
