Problema · 01

¿Por qué Kubernetes para AI?

Cuatro razones reales — todas, primitives que ya conocés.

01

GPU scheduling

El kernel del scheduler ya gestiona recursos escasos. Una GPU es solo otro resources.limits.

02

Autoscaling para cargas spiky

Inferencia es ráfagas, no constante. HPA y KPA están hechos para eso.

03

Multi-tenancy

Múltiples modelos, múltiples equipos, mismo cluster. Namespaces y RBAC.

04

Ecosystem maduro

Observability, ingress, secrets, network policies. Ya están — no se reinventan para AI.

Problema · 02

Servir un modelo no es flask + model.predict()

LO INGENUO
@app.post("/predict")
def predict(img):
    return model.predict(img)
Funciona en una laptop. No en producción.
LO QUE NECESITÁS
  • Batching — usar la GPU eficientemente
  • GPU mgmt — scheduling, isolation
  • Queueing — cuando llegan más requests que las que el modelo procesa
  • Observability — métricas de inferencia
  • Rollouts — un modelo nuevo puede ser peor
  • Versioning — A/B, canary, traffic split

Implementación · 03

¿Por qué K3s?

  • 1 nodo, 1 binario, ~50 MB.
  • Install en 60 segundos.
  • Trae Traefik, ServiceLB y local-path-provisioner.
  • Soporta los CRDs que KServe v0.14 requiere.
  • Suficiente para serving single-node.
# un comando
$ curl -sfL https://get.k3s.io | sh -

$ kubectl get nodes

gpu-node   Ready    v1.34.1+k3s1

Implementación · 04

¿Por qué RawDeployment?

Con 1 GPU, scale-to-zero no aporta valor — y agrega cosas que pueden fallar.

RAWDEPLOYMENT  ·  ELEGIDO
  • 1 GPU dedicada → no hay nada a qué escalar a cero
  • El modelo tarda ~1 min en cargar → cold start dolería
  • Menos componentes = menos cosas que fallan
KNATIVE  ·  DESCARTADO
  • Activator + Autoscaler + Istio extras
  • Cold starts visibles para el usuario
  • Vale la pena cuando hay muchos modelos, tráfico bursty

Decisión · 01

Runtime built-in de HuggingFace — demasiado viejo

CONTEXTO
KServe v0.14 trae un huggingfaceserver con vLLM bundled — pero la versión que trae no reconoce qwen3_vl.
CONSTRAINT
Necesito Qwen3-VL → necesito vLLM ≥ 0.10.x.
DECISIÓN
ServingRuntime custom apuntando a vllm/vllm-openai.
apiVersion: serving.kserve.io/v1alpha1
kind: ServingRuntime
metadata:
  name: vllm-runtime
spec:
  supportedModelFormats:
    - name: vllm
  containers:
  - name: kserve-container
    image: vllm/vllm-openai:v0.11.0

Decisión · 02

hf:// no es URI válido en KServe v0.14

CONTEXTO
Quiero apuntar al modelo en HuggingFace Hub:
hf://Qwen/Qwen3-VL-4B-Instruct.
ERROR
Invalid value: "hf://...":
storageUri must be one of:
  gs:// | s3:// | pvc:// |
  file:// | https://
DECISIÓN
Hardcodear el HF model id en --model y dejar que vLLM lo descargue al startup.
args:
  - --model=Qwen/Qwen3-VL-4B-Instruct
  - --dtype=float16
  - --max-model-len=8192
Costo: descarga al primer arranque del pod.

Decisión · 03

vLLM image pin: v0.11.0

CONTEXTO
Hay dos restricciones simultáneas: el modelo y el driver del host.
VENTANA VÁLIDA
v0.10.x
no qwen3_vl
v0.11.0 ✓
CUDA 12.x
v0.11.1
CUDA 12.x
v0.11.2
CUDA 13
v0.12+
CUDA 13
CONSTRAINT
  • v0.10.x no soporta qwen3_vl
  • v0.11.2+ usa CUDA 13
  • Host driver = CUDA 12.8
DECISIÓN
image: vllm/vllm-openai:v0.11.0
# nunca :latest
KServe no sabe qué CUDA tiene tu driver. Esta decisión es tuya.

Decisión · 04

Rollout strategy: Recreate

CONTEXTO
Con 1 GPU schedulable, RollingUpdate genera deadlock:
$ kubectl get pods
vllm-old-xxx    Running   2d
vllm-new-yyy    Pending   ∞
# Insufficient nvidia.com/gpu
Pod nuevo espera la GPU. Pod viejo no la libera hasta que el nuevo esté Ready. Deadlock.
DECISIÓN
$ kubectl patch deploy/vllm-predictor \
   -p '{"spec":{"strategy":{
       "type":"Recreate"}}}'
Cuando un recurso es scarce (GPU, IP estática, port host) → Recreate. ~30s downtime, pero el rollout completa.

Implementación · 11

La capa de API — dos backends

Dev local con Ollama, prod con vLLM. Ambos exponen API compatible OpenAI — el código es el mismo.

# apps/api/app/ocr.py
def get_client():
    backend = os.getenv("OCR_BACKEND", "vllm")
    if backend == "ollama":
        return OpenAI(
            base_url="http://localhost:11434/v1",
            api_key="ollama",
        )
    # vllm via KServe
    return OpenAI(
        base_url="http://qwen3-vl-predictor/v1",
        api_key="not-needed",
    )
DEV
OCR_BACKEND=ollama → laptop
PROD
OCR_BACKEND=vllm → cluster
Mismo código de la API. Solo cambia la base_url.

Lo que funciona  ·  los caveats

FUNCIONA
~5–9s
latencia end-to-end por imagen
(mayor parte = inferencia del modelo)
  • JSON estructurado consistente
  • MRZ valida en pasaportes legibles
  • Encadenable con el resto del sistema
CAVEATS
  • Pasaportes muy dañados → no hay override determinístico
  • MRZ ilegible → cae al modelo solo
  • Latencia no es interactiva fina — útil para batch o async
